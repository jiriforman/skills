# JIRA Report Generator

Generate an interactive, CETIN-branded HTML dashboard from a JIRA CSV export.

## When to Use

- User uploads a JIRA CSV (filename often contains "jira", "issues", "export")
- User asks for a JIRA dashboard, status report, sprint report, or aging analysis
- User wants a shareable HTML view of JIRA data (no live API needed)

## When NOT to Use

- User wants to create/update JIRA tickets → not supported here
- User wants live JIRA data → this skill works only on a static CSV export
- User wants a PowerPoint or Word version → invoke `pptx` or `docx` instead
- User wants raw Excel pivots → invoke `xlsx` skill

## Workflow

### Step 1 — Locate the CSV

1. Check `input/` for a `.csv` file (use `Glob input/**/*.csv`)
2. If multiple CSVs exist, ask the user which one
3. If none found, tell the user: "I don't see a JIRA CSV in your materials — please upload it and I'll pick it up."

### Step 2 — Inspect & validate

Read the first 5 rows to confirm it's a JIRA export. Expected columns typically include:
`Issue key`, `Summary`, `Issue Type`, `Status`, `Priority`, `Assignee`,
`Reporter`, `Created`, `Updated`, `Resolved`, `Due Date`,
`Sprint`, `Story Points`, `Project key`, `Project name`,
`Epic Link` / `Parent`, `Components`, `Labels`, `Resolution`

JIRA exports sometimes duplicate columns (e.g. multiple `Sprint` or `Component`
columns). The analyzer coalesces same-named columns into a list per row.

If required columns are missing, surface what's missing and ask the user to
re-export with those fields.

### Step 3 — Compute metrics

Run the analyzer:

```bash
python scripts/analyze_jira.py --input "<path-to-csv>" --output working/jira_metrics.json
```

It computes:

**A. Status overview**
- Issue count by Status (Open, In Progress, In Review, Done, etc.)
- Issue count by Issue Type (Story, Bug, Task, Epic, Sub-task)
- Issue count by Priority
- Issue count by Assignee (top 15, rest grouped as "Other")

**B. Sprint / velocity**
- Current sprint name(s) — detected from `Sprint` column
- Story points: planned vs completed for current sprint
- Velocity trend: completed story points per past sprint (last 6)
- Sprint scope: count of issues per sprint

**C. Aging & blockers**
- Open issues older than 14 / 30 / 60 / 90 days (Created vs today)
- Issues not updated in 14+ days
- Blocked issues (Status contains "Block" OR Priority = "Blocker" OR has "blocked" label)
- Top 10 oldest open issues (key, summary, age, assignee)

**D. Project / epic breakdown**
- Counts per Project key
- Counts per Epic Link with % done (Done ÷ Total)
- Components breakdown (top 10)

Output written to `working/jira_metrics.json`.

### Step 4 — Apply CETIN branding

Invoke the `cetin-design` skill to load the CETIN brand tokens (CETIN Blue
`#003DA5`, CETIN Red, Avenir/Arial, logo). The renderer reads these tokens.

### Step 5 — Render the HTML dashboard

```bash
python scripts/render_dashboard.py --metrics working/jira_metrics.json --output output/jira-report.html
```

Structure:
1. **Header** — CETIN logo, report title, generated-on date, source filename
2. **KPI strip** — 5 KPI cards: Total issues, Open, In Progress, Done %, Blockers
3. **Status overview** — donut chart (status) + bar chart (issue type) + bar chart (assignee)
4. **Sprint & velocity** — current sprint progress bar + velocity bar chart (last 6 sprints)
5. **Aging & blockers** — aging buckets bar chart + table of top 10 oldest open
6. **Projects & epics** — project counts table + epic progress bars
7. **Footer** — "Generated by Copilot Cowork" + timestamp

Rendering rules:
- Self-contained HTML (inline CSS, inline SVG charts, no external CDNs)
- Pure SVG bars/donuts — no JS chart library dependency
- CETIN Blue for primary, CETIN Red for blockers/overdue
- Responsive layout (CSS grid, breaks at 900px)
- Print-friendly (`@media print` rules)
- Tables sortable client-side via small inline vanilla JS

### Step 6 — Deliver

1. Confirm the file exists: `Glob output/**/*`
2. Tell the user: "Your JIRA report is ready — saved as `jira-report.html` in your files."
3. Inline summary in chat: total issues, % done, # blockers, # aging >30d, active sprints

## Output

- `output/jira-report.html` — the dashboard (always)
- `working/jira_metrics.json` — computed metrics (intermediate, for transparency)

## Guardrails

- Never invent numbers — every metric must trace to the CSV
- If a column is missing, omit that section and note it in the report
- Cap rendered tables at 50 rows; offer to widen on request
- Assignee names shown as in the CSV (no auto-anonymisation)
- Purely local CSV → HTML; no external service calls

## Edge Cases

- **Empty CSV / no rows** → report "No issues found in the export" and stop
- **All issues Done** → still render, with 100% done and no aging section
- **No Sprint column** → omit Sprint section, note in report
- **Multi-value cells** (Components, Labels) → split on `,` or `;`
- **Date parsing** — JIRA uses `dd/MMM/yy HH:mm` or ISO 8601; try both
- **Very large CSV (>10k rows)** → process, but warn about render time
